# Схема базы данных SQLite

[English](DATABASE.md) | [Русский](DATABASE.ru.md) | [Основной README](README.ru.md) | [Архитектура](ARCHITECTURE.ru.md)

## Расположение и жизненный цикл

`tags.sqlite3` создаётся рядом с `TagFinder.exe`. Используется абсолютное
расположение EXE, а не рабочая папка оболочки. SQLite встроена в приложение.
Перед переносом EXE и БД закройте программу. Отдельный сервер не нужен.
Пути внутри индекса остаются привязаны к расположениям последнего сканирования.

При запуске `IF NOT EXISTS` создаёт недостающие таблицы и индексы, затем
восстанавливаются настройки. Существующие связи не удаляются, сканирование
автоматически не начинается.

## Полная схема приложения

```sql
CREATE TABLE IF NOT EXISTS uses (
    tag  TEXT NOT NULL,
    path TEXT NOT NULL,
    PRIMARY KEY (tag, path)
);

CREATE INDEX IF NOT EXISTS tag_lookup
    ON uses(tag COLLATE NOCASE);

CREATE TABLE IF NOT EXISTS settings (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

### `uses`: где встречается тег

| Поле | Значение | Пример |
| --- | --- | --- |
| `tag` | Извлечённое имя с исходным регистром и разрешёнными символами. | `Me.UPSStatus_BF` |
| `path` | Полный путь исходного файла, передаваемый в SQLite как UTF-8. | `C:\Layouts\Screen_01.$view` |

Это прямая таблица связи «многие ко многим»: один тег встречается в нескольких
файлах, а один файл содержит несколько тегов. Отдельных таблиц `tags`/`files`,
числовых идентификаторов и внешних ключей нет. Первичный ключ `(tag, path)`
не допускает повторной записи одной пары. Число вхождений и смещения байтов
не хранятся. У файла без принятых имён нет строки, даже если он вошёл в счётчик
обработанных файлов. Имя файла для интерфейса вычисляется из `path`.

Пример:

| tag | path |
| --- | --- |
| `Me.UPSStatus_BF` | `C:\Layouts\Overview.bin` |
| `Me.UPSStatus_BF` | `C:\Layouts\Power.bin` |
| `$Pump-01.Status` | `C:\Layouts\Overview.bin` |

Первые две строки показывают, где используется `Me.UPSStatus_BF`. Первая и
третья показывают, что в `Overview.bin` содержится больше одного имени.

**Регистр:** первичный ключ использует стандартное сравнение SQLite `BINARY`.
Поэтому `Pump.Run` и `pump.run` — разные сохраняемые имена. Поиск игнорирует
регистр и может вернуть оба. `tag_lookup` с `NOCASE` ускоряет точный поиск,
но не меняет правила уникальности. Встроенное преобразование регистра SQLite
ориентировано на ASCII, что соответствует допустимому алфавиту тегов.
Написание путей БД глобально не нормализует: разный регистр пути даёт разные ключи.

### `settings`: последнее успешное сканирование

| `key` | Значение `value` | Назначение |
| --- | --- | --- |
| `scan_folder` | Абсолютный путь папки в UTF-8. | Заполняет поле папки при следующем запуске. |
| `scan_recursive` | Текст `"1"` или `"0"`. | Восстанавливает флажок Include subfolders. |

До первого сканирования строк может не быть. По умолчанию папка пуста, а обход
вложенных папок включён. Настройки записываются только при успешном сканировании.
Приложение всегда передаёт фиксированные ненулевые ключи. Выше приведена
фактическая схема, без дополнительных ограничений или проверок.

Дата сканирования, поисковая строка, времена изменения файлов и хеши не
сохраняются. Поэтому обновление каждый раз обходит всю выбранную область.

## Транзакция замены

`scan()` выполняет на одном соединении:

```sql
BEGIN IMMEDIATE;
DELETE FROM uses;
-- Подготовленные запросы повторяются; значения привязываются к параметрам ?:
INSERT OR IGNORE INTO uses(tag, path) VALUES (?, ?);
INSERT OR REPLACE INTO settings(key, value) VALUES (?, ?);
COMMIT;
```

Запись настроек выполняется по одному разу для каждого известного ключа.
Удаление, новые связи и настройки фиксируются вместе. Ошибка обхода или SQL
приводит к освобождению запросов/соединения и откату незавершённой транзакции:
старый снимок сохраняется. Отдельные недоступные файлы пропускаются без отката;
при успешной фиксации их старые связи исчезают.

Успешный запуск заменяет все строки `uses`, включая результаты другой ранее
выбранной папки. Для общего индекса нескольких папок выбирайте общего родителя.
Удалённые файлы и исчезнувшие имена пропадают после следующего успешного обновления.

При запуске выбираются `journal_mode=DELETE` и `synchronous=FULL`, ожидание
блокировки соединения — до 5 секунд. Во время записи возможен временный
`tags.sqlite3-journal`. Завершённая транзакция удаляет его, и после обычного
выхода остаётся одна БД. После аварии сначала откройте приложение для
восстановления SQLite и лишь затем переносите файлы; не удаляйте журнал
восстановления вручную.

## Поисковые запросы

Точное совпадение без учёта регистра:

```sql
SELECT tag, path FROM uses
WHERE tag = ? COLLATE NOCASE
ORDER BY tag, path
LIMIT 5001;
```

Буквальная подстрока без учёта регистра:

```sql
SELECT tag, path FROM uses
WHERE instr(lower(tag), lower(?)) > 0
ORDER BY tag, path
LIMIT 5001;
```

В `?` передаётся связанный UTF-8-параметр, а не склеенный SQL. Пустой поиск
интерфейс не выполняет. `instr` не интерпретирует пунктуацию как шаблон `LIKE`.
Подстрочный поиск обычно просматривает таблицу, а не использует индексный поиск
по равенству. Показывается не более 5 000 строк; дополнительная строка выявляет
превышение лимита.

Примеры ручной проверки в клиенте SQLite (для работы программы он не нужен):

```sql
SELECT COUNT(*) AS relationships FROM uses;
SELECT COUNT(DISTINCT tag) AS distinct_names FROM uses;
SELECT COUNT(DISTINCT path) AS files_with_tags FROM uses;
SELECT tag FROM uses WHERE path = 'C:\Layouts\Overview.bin' ORDER BY tag;
SELECT key, value FROM settings ORDER BY key;
```

`files_with_tags` не равно общему числу просмотренных файлов: файлы без тегов
не представлены. Приложение читает формы без записи; изменяется только его индекс.
